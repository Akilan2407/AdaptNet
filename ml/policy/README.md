# Phase 13 — QoS Policy Engine Module

Part of the **“Explainable, User-Aware ML System for Adaptive Network Traffic Management in Small LANs”** project.

---

> [!IMPORTANT]
> **No Actual Network Control in Phase 13**
> The Phase 13 QoS Policy Engine generates transparent policy decisions. It does not yet apply those decisions to the actual network.
> Actual network enforcement (such as Linux `tc`, socket modifications, packet marking, or traffic shaping) is strictly reserved for **Phase 14 — Adaptive Traffic Control Module**.

---

## 1. Purpose & Motivation

The **QoS Policy Engine** serves as the decision-making brain of the adaptive network traffic management architecture. Rather than using an opaque black-box machine-learning model for priority assignment, Phase 13 implements a **deterministic, configurable, transparent, explainable, and rule-based policy engine**.

The engine synthesizes three distinct layers of telemetry:
```text
User Behavior Profile (Phase 8)
              +
Traffic Classification (Phase 12)
              +
Predicted Congestion (Phase 10)
              ↓
      QoS Policy Engine
              ↓
       Priority Decision
```

Key architectural guarantees:
* **Deterministic**: Identical flow contexts consistently generate identical QoS priority decisions.
* **Configurable**: Priority tables, congestion thresholds, and profile adjustment mappings are centralized in configuration.
* **Transparent & Explainable**: Every decision traces directly to a specific rule ID and includes a human-readable justification.
* **No Black-Box Actuation**: The engine contains **no additional machine learning model** or reinforcement learning agent.

---

## 2. Multi-Source Inputs

The policy engine consumes outputs from three preceding project phases:

```text
data/profiling/behavior_profiles.csv   ───────┐
                                               ▼
data/congestion/test_predictions.csv   ──► [ QoS Policy Engine ] ──► data/policy/qos_decisions.csv
                                               ▲
data/classification/classified_flows.csv ──────┘
```

The engine accepts a structured context containing:
* `device_id` (e.g. `h1`)
* `flow_id` (e.g. `h1_192.168.1.10:45672->192.168.1.11:5201_TCP`)
* `traffic_class` (`REAL_TIME`, `INTERACTIVE`, `WEB`, `DNS`, `BULK_TRANSFER`, `OTHER`)
* `classification_confidence` (0.0 to 1.0)
* `predicted_congestion_score` (0.0 to 1.0, or None)
* `predicted_congestion_class` (`LOW`, `MEDIUM`, `HIGH`, or `UNKNOWN`)
* `cluster_id` (0, 1, or None)
* Optional flow metadata when available: `throughput_mbps`, `rtt_ms`, `packet_loss_percent`, `active_connections`.

---

## 3. Traffic Classification Input (Phase 12)

The engine receives classified traffic labels from `data/classification/classified_flows.csv`:
* `REAL_TIME`: Real-time media streams (RTP, STUN/TURN, SIP) requiring minimal jitter and delay.
* `INTERACTIVE`: Low-volume interactive control flows (SSH, RDP, Telnet) requiring responsive round-trip times.
* `WEB`: Standard web transactions (HTTP, HTTPS, HTTP/3).
* `DNS`: Domain resolution queries where timeouts degrade application startup.
* `BULK_TRANSFER`: Bandwidth-heavy, delay-tolerant transfers (iPerf3 benchmarks, file downloads, SMB).
* `OTHER`: Unclassified or unrecognized port/protocol flows.

---

## 4. Congestion Prediction Input (Phase 10)

Congestion predictions are drawn from `data/congestion/test_predictions.csv` (generated by the Phase 10 GRU model):
* `predicted_congestion_score`: Floating-point congestion index in $[0.0, 1.0]$.
* `predicted_congestion_class`: Categorical congestion state defined in Phase 9 (`data/congestion/congestion_label_config.json`):
  * `LOW` ($[0.0, 0.33)$): Abundant LAN bandwidth, low latency, negligible queuing delay.
  * `MEDIUM` ($[0.33, 0.67)$): Moderate queuing, requiring early priority differentiation.
  * `HIGH` ($[0.67, 1.0]$): Severe congestion risk, requiring strict preference for latency-sensitive traffic and deprioritization of bulk transfers.
  * `UNKNOWN`: Missing prediction telemetry (fallback to baseline rules).

---

## 5. User Behavior Input (Phase 8) & Cluster Neutrality

User behavior telemetry is supplied from `data/profiling/behavior_profiles.csv`:
* `device_id`: Device identifier.
* `cluster_id`: Mathematical cluster index assigned via K-Means unsupervised clustering in Phase 8.

### Important Design Rule: Cluster Neutrality
K-Means cluster IDs (e.g. Cluster 0 vs Cluster 1) are purely mathematical identifiers. They are **never assumed to be inherently good or bad**:
* Cluster 0 is **not** assumed to be "low priority".
* Cluster 1 is **not** assumed to be "high priority".

Any behavioral adjustment applied to a cluster must be explicitly configured via `CLUSTER_ADJUSTMENTS` in `config.py` based on transparent administrative intent. By default, `CLUSTER_ADJUSTMENTS = {0: 0, 1: 0}` (neutral adjustment).

## 7. Priority Levels & Numerical Scale

QoS priorities are represented as discrete policy labels and mapped to an internal $[0, 3]$ scale:

```text
Scale Value    Priority Label    Description
---------------------------------------------------------------
3              HIGH              Flow receives strongest QoS preference
2              MEDIUM            Moderate QoS preference
1              NORMAL            Default baseline handling
0              LOW               Lowest QoS preference
```

Helper utilities in `ml/policy/priority.py`:
* `priority_to_numeric(priority: str) -> int`: Validates and maps label to 0–3.
* `numeric_to_priority(value: int) -> str`: Converts numeric values back to label with strict boundary clamping.
* `apply_priority_adjustment(base_priority: str, adjustment: int) -> Tuple[str, int]`: Applies arithmetic adjustment and clamps within $[0, 3]$.

Boundary clamping guarantees:
$$\text{Priority}_{\text{clamped}} = \max\left(0, \min\left(3, \text{Priority}_{\text{base}} + \Delta_{\text{adj}}\right)\right)$$

## 8. Rule Evaluation Pipeline Order

The policy engine executes a strict 9-step evaluation pipeline for every flow context:

```text
1. Validate input context schema and normalize data types
2. Determine traffic category (fallback to OTHER if unrecognized)
3. Determine congestion class (fallback to UNKNOWN if unmeasured)
4. Determine default baseline traffic priority
5. Match rule and apply congestion-aware resolution
6. Apply optional user-profile cluster adjustment
7. Clamp final priority within [0, 3] (LOW to HIGH)
8. Generate human-readable explainable reason string
9. Generate structured decision record dictionary
```

---

## 9. User-Profile Adjustments

User profile adjustments allow administrative tuning based on device behavior patterns:
* Configured in `CLUSTER_ADJUSTMENTS` within `ml/policy/config.py`:
  ```python
  CLUSTER_ADJUSTMENTS = {
      0: 0,   # Cluster 0 neutral adjustment
      1: 0,   # Cluster 1 neutral adjustment
  }
  ```
* If a custom profile policy is enabled (e.g. `CLUSTER_ADJUSTMENTS = {1: +1}`), the engine applies $\Delta = +1$, increasing the flow's priority by one rank up to the maximum clamp of `HIGH` (3).
* If `cluster_id` is missing or unconfigured, `user_profile_adjustment = 0`.

---

## 10. Decision Reason Generation & Explainability

Every generated decision includes a clear, human-readable justification synthesized by `ml/policy/decision_reason.py`. Vague explanations such as "AI decided this" are strictly prohibited.

Examples:
* `BULK_TRANSFER traffic during MEDIUM predicted congestion received LOW priority.`
* `REAL_TIME traffic during HIGH predicted congestion received HIGH priority to preserve latency sensitivity.`
* `BULK_TRANSFER traffic with UNKNOWN predicted congestion received default base priority LOW.`
* `Base priority MEDIUM was increased to HIGH because the configured user-profile adjustment was +1 (cluster 2).`

---

## 11. Missing-Data Behavior & Input Completeness

The engine gracefully handles incomplete telemetry:
* **Missing Cluster**: If `cluster_id` is absent, `user_profile_adjustment = 0`.
* **Missing Congestion Prediction**: If no congestion prediction exists for the device within the temporal alignment window, `predicted_congestion_class = "UNKNOWN"`, and the engine falls back to `POLICY_UNKNOWN_CONGESTION_FALLBACK`.
* **Missing Traffic Class**: Defaults to `OTHER`.

The decision records input quality via `input_completeness`:
* `COMPLETE`: Traffic class, congestion prediction, and cluster ID are all verified and known.
* `PARTIAL`: One or more inputs were missing or fell back to default assumptions.

## 13. Limitations & Small LAN Context

* **Offline / Batch Telemetry**: Evaluations in Phase 13 process historical flows captured during test runs. Real-time online streaming evaluation will be connected in subsequent phases.
* **Dataset Traffic Mix**: The current monitored test dataset primarily features high-throughput iPerf3 benchmark flows (`BULK_TRANSFER`). Multi-class edge cases (`REAL_TIME`, `DNS`, `WEB`) are verified via the 16 unit tests.
* **No Actuation**: Decisions are advisory policy labels and do not modify Linux networking interfaces.

## 16. Relationship with Phase 15 (Explainability & Traceability)

* Phase 13 records the foundational decision trail (`policy_rule_id`, `policy_reason`, `base_priority`, `congestion_adjustment`, `user_profile_adjustment`, `input_completeness`).
